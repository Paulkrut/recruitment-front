## 1. Фактическая карта продукта

## 2. Реестр несоответствий и будущие тесты

### C01. Изоляция компаний допускает fail-open — P0, высокая уверенность в коде

`B/src/EventListener/CompanyContextListener.php:43–51` возвращается без company при отсутствии заголовка. `B/src/Controller/ValueResolver/CompanyOwnedValueResolver.php:56–62` при отсутствии company возвращает найденную entity без проверки владельца. Дополнительно `B/src/Controller/Api/AdminVacancyController.php:789–840` обновляет найденную по ID вакансию и вопросы без CompanyOwned/сравнения компании. `B/src/Controller/Api/AdminCandidateController.php:84–95` принимает произвольный vacancyId при ручном создании кандидата.

Роль/риск: работодатель, межфирменный доступ или изменение данных. Это статически обоснованный дефект, не утверждение о состоявшейся утечке. Проверка: только на двух полностью синтетических компаниях A/B; войти A, открыть свою карточку, перехватить её GET и повторить с заранее выданным ID B без X-Company-ID; ожидать 403/404. Для PUT — только одноразовая тестовая вакансия B с сохранённой копией, отдельное разрешение на изменение. Сейчас ничего не выполнялось. До привлечения командного трафика нужна приоритетная проверка границ.

### C02. detect-ai-resume: отсутствующая серверная реализация — P1, высокая уверенность в локальной причине

UI `/hr-tools/ai-detector` существует и вызывает useAiDetector: `F/src/app/hr-tools/ai-detector/AiDetectorClient.tsx:23–56`. Хук POST на `/api/public/hr-tools/detect-ai-resume`: `F/src/app/hr-tools/hooks/useHrTool.ts:37–48`, `:257–260`. В backend поиск по `detect.ai.resume`, `detectAiResume`, `AiDetector` совпадений не дал; `B/src/Controller/Api/HrToolsController.php:24` содержит другие инструменты, маршрута детектора нет. Роуты импортируют атрибуты контроллеров: `B/config/routes.yaml:1–5`; security разрешает общий public prefix: `B/config/packages/security.yaml:93–94`.

Root cause локального контракта: frontend опубликовал UI и endpoint, отсутствующий в исследованном backend; не проблема порога 100 символов, согласия или типа результата. При таком комплекте ожидается route not found; возможная HTML-ошибка затем неудачно парсится response.json, маскируя причину. Production-статус/HTTP-код не проверены, там может быть иной релиз/прокси.

Будущий тест: заранее убедиться, что целевой сервер не реализует платную обработку; открыть инструмент, вставить синтетический текст >100 символов, дать тестовое согласие, один раз отправить и зафиксировать URL/status/body без ПДн. Не считать наличие страницы доказательством работающего детектора и не рекламировать достоверность вероятности AI.

### C03. Удаление после интервью: разрыв маршрута и модели — P1, высокая уверенность

UI handleForgetMe обращается к `/api/interview/{token}/forget-me` без JWT: `F/src/app/interview/[token]/page.tsx:1477–1505`. Реальный маршрут — `/api/public/interview/{token}/forget-me`: `B/src/Controller/Api/PublicInterviewController.php:37`, `:1386`. Старый URL не найден, защищён общим `/api` правилом. Даже исправление URL не доказывает исправность: handler ищет InterviewSession по token (`:1397`), хотя token принадлежит Candidate, а в `B/src/Entity/InterviewSession.php:10–55` такого поля нет. Далее sessRepo используется как список ответов (`PublicInterviewController.php:1425–1436`), с вызовами методов медиа у сессий.

Будущий тест: завершённый одноразовый синтетический кандидат → открыть удаление → ввести УДАЛИТЬ → проверить запрос и фактическое отсутствие записей/файлов в тестовом контуре. Не выполнять на реальных данных. Отдельные endpoints PrivacyController не доказывают работу именно этой кнопки.

### C04. Успешная оплата вызывает отсутствующий метод — P0/P1, высокая уверенность

`B/src/Service/YookassaService.php:283–291` после addInterviewsFromPayment вызывает `$plan->getIncludedInterviews()`. В `B/src/Entity/SubscriptionPlan.php:102` есть только getInterviewsIncluded; полный поиск getIncludedInterviews находит только ошибочный вызов. Начисление flush выполняется раньше (`B/src/Service/BillingService.php:190–222`), поэтому нельзя утверждать, что деньги/баланс обязательно потеряются; вероятен разрыв обработки webhook/уведомлений после изменения данных. Внешние catch ловят Exception, а undefined method — Error.

Будущий тест: только YooKassa test-shop или локальная фикстура succeeded payment, без реального платежа; провести один тестовый платёж, проверить callback/status, начисление ровно один раз, повтор webhook, журнал ошибок. Дополнительный вопрос P0: публичный webhook принимает body и меняет статус без видимой в этих методах перепроверки платежа у YooKassa (`YookassaService.php:187–238`, `YookassaWebhookController.php:28–49`); сетевой allowlist/WAF не проверен. До теста проверить инфраструктурную верификацию; не отправлять поддельные события в production.

### C05. Регистрация зависит от email, UI игнорирует его неотправку — P1/P2, высокая уверенность

Backend сохраняет аккаунт и возвращает success даже при emailSent=false (`B/src/Controller/Api/AuthController.php:100–114`, `:144–148`). Пароль пользователь заранее не задаёт. UI любой response.ok считает успехом и уводит на вход (`F/src/app/auth/register/page.tsx:159–164`). Дополнительно согласие на маркетинг отправляется как marketing_opt_in (`:153`), а backend записывает marketing (`AuthController.php:123`).

Будущий тест: sandbox-mailer с управляемым отказом → синтетическая регистрация → оценить сообщение, возможность входа и восстановления; отдельно true/false маркетинга сопоставить с consent log. Только с предварительным разрешением создания аккаунта; административный Telegram должен быть отключён.

### C06. Новая компания и тарифный UI расходятся с настройками backend — P2, высокая/средняя

Регистрация начисляет DB free-бонус, ручное создание компании этого не делает (ссылки в карте). Поэтому «10 бесплатно» в `F/src/app/hr-tools/ai-detector/AiDetectorClient.tsx:128` — текст, не гарантия любой компании. Бесплатные тесты/скрининги в UI всегда отмечены true (`F/src/app/(DashboardLayout)/hr/billing/page.tsx:163–169`), backend проверяет параметры/дату (`B/src/Service/BillingService.php:409–422`, `:438–451`). Точные значения окружения/БД не исследовались.

Будущий тест: две подготовленные компании — после регистрации и созданная вручную; сравнить balance, free plan, возможность запуска при 0. Согласовать expected policy для trial и тестов, проверить UI при отключённом free-флаге. Не активировать тариф/не запускать AI без разрешения.

### C07. «Подарочное» списание не равно реальному дебету — P2, высокая уверенность

BillingService помечает billingProcessed и создаёт debit(-1), игнорируя bool deductInterview (`B/src/Service/BillingService.php:552–574`). Entity при балансе ≤0 возвращает false и НЕ меняет баланс/total used (`B/src/Entity/CompanyBalance.php:167–176`). Комментарий про уход в минус не соответствует entity. В разных статистиках возможны разные знаменатели; флаг сам по себе не доказывает атомарность при параллельных workers.

Будущий тест: локальная фикстура двух сессий и баланс 1 → имитация успешного анализа без AI → сравнить balance, entity lifetime, ledger, gifted и повторную обработку. Нужен контролируемый конкурентный тест, не реальный кандидат. Не считать расхождение доказанным финансовым ущербом.

### C08. Кнопка добавления в kanban — заглушка, другой путь реализован — P2/P3, высокая уверенность

`F/src/app/(DashboardLayout)/hr/vacancies/[id]/KanbanView.tsx:1536–1542`: onClick содержит только TODO. При этом реальный handler добавления кандидата есть в page.tsx:1918 и API реализован. Нельзя объявлять «ручное добавление отсутствует» целиком.

Будущий UI-тест: открыть kanban → нажать «Добавить кандидата» в колонке → проверить отсутствие модалки/запроса; сравнить с общим добавлением в карточке. Для первой части запись данных не требуется.

### C09. Отчёт и статусы не гарантируют автообновление — P2, высокая уверенность в локальном UI

Карточка кандидата загружает status/evaluation однократно по token/id (`F/src/app/(DashboardLayout)/hr/candidates/[id]/page.tsx:150–166`); status label AI обрабатывает done/pending, прочее — «Нет данных» (`:686–687`). Worker выставляет in_progress (`B/src/MessageHandler/EvaluateCandidateHandler.php:120`), API возвращает статус как есть (`B/src/Controller/Api/AdminCandidateController.php:384–397`). Отдельный хук `F/src/hooks/useCandidateEvaluation.ts:113–128` poll только pending и не используется карточкой как хук (импортируется лишь тип). Сессия завершена в backend как finished (`B/src/Entity/InterviewSession.php:23`), а часть UI сравнивает completed (`.../candidates/[id]/page.tsx:532`, `:960`). API finishedAt всегда null (`B/src/Controller/Api/InterviewSessionAdminController.php:320`).

Будущий тест: открыть отчёт до завершения фоновой задачи, удержать worker для наблюдения pending/in_progress/done, проверить обновление без reload, затем после reload; сравнить надписи и таймстемпы. Не путать готовность интервью, AI-отчёта и email-результата.

## 3. Командные права: что есть и чего не доказано

Фактическая модель — membership компании и HR/HR_LEAD. UI сотрудников скрывает/разрешает управление на основании роли (`F/src/app/(DashboardLayout)/hr/employees/page.tsx:36–48`). Backend приглашать, удалять, повышать и отзывать приглашения разрешает HR_LEAD; читать список разрешено членам (`B/src/Controller/Api/CompanyController.php:50–62`, `:113–144`, `:194–237`). Принятие сверяет email авторизованного пользователя (`:158–177`); ссылка ведёт на choose-company, не даёт независимый гостевой доступ (`:85–86`).

BillingController требует ROLE_USER, а не HR_LEAD (`B/src/Controller/Api/BillingController.php:21–23`, `:144`); конкретное наличие ROLE_USER/иерархия требует проверки тестовой роли. Не найдено в исследованных местах модели hiring-manager/view-only/per-vacancy permission. Это не полный security audit и не доказательство отсутствия модели во всём проекте. Нужна явная проверка обычного HR на чтение/изменение вакансий, отчётов, оплату, приглашения и cross-company сценарии C01.

## 4. Аналитические события и ограничения воронки

- Метрика инициализируется с webvisor, clickmap, ecommerce:dataLayer: `F/src/components/YandexMetrika.tsx:10–24`. Поиск по src `reachGoal|trackEvent|dataLayer|gtag\(|ym\(` нашёл только инициализацию. Явные бизнес-цели регистрации → компании → вакансии → приглашения → интервью → отчёта → оплаты в исследованном frontend не найдены. Это не доказывает отсутствия целей по URL/кликам или настроек в кабинете Метрики.
- Backend имеет CandidateEvent: candidate_created, hh_message_sent, auto_invite/reminder/reject, interview_started/completed и изменения статусов: `B/src/Service/CandidateEventLogger.php:23–196`; события доступны в карточке: `B/src/Controller/Api/AdminCandidateController.php:750`.
- Покрытие неоднородно: найденный вызов logCandidateCreated — в CandidateConversionService:84; ручной createCandidate и public apply не вызывают этот logger в прочитанных реализациях. Для воронки по всем источникам нельзя считать CandidateEvent полным реестром созданий.
- В PublicInterviewController есть несколько мест logInterviewCompleted (:539, :1097, :1172). Их наличие не доказывает дубли на реальном пути, но требует проверить уникальность candidate/session/event и denominator перед подсчётом completion rate.
- Финансовые Transaction/Payment, статусы сессии/оценки, CandidateEvent можно сопоставлять в тестовом/обезличенном серверном отчёте. Посещение interview, start, finished, evaluation done, просмотр HR-отчёта и payment succeeded — разные события. Событие просмотра работодателем готового отчёта не найдено в прочитанных местах.
- `/hr/billing/analytics` — аналитика потребления/покупок, не автоматически сквозная маркетинговая атрибуция. Демо-данные и бонусы нужно отделять от первых реальных результатов/покупок.

Будущий тест измерений: на одном синтетическом сценарии фиксировать времена и обезличенные session/candidate/company IDs, сопоставить сетевые запросы, DB события, Метрику и платежный sandbox. Проверить начало, завершение, ready report, факт просмотра, повторное использование, оплату отдельно; не менять цели production в исследовательском тесте.

## 5. Нужные доступы и безопасные условия для сквозной проверки

1. Изолированный staging с известными версиями frontend/backend, отдельной БД и возможностью отката; список внешних побочных эффектов. Не копия реальных кандидатов.
2. Заранее подготовленные синтетические аккаунты HR_LEAD и HR компании A, HR_LEAD компании B; одноразовые вакансии, критерии и кандидаты. Для invited-user сценария — ещё один заранее разрешённый тестовый email/аккаунт под контролем владельца. Реальные кандидаты и посторонние приглашённые не нужны.
3. Sandbox-mailer/перехват писем; отключённый административный Telegram, digest/reminder/auto-invite/auto-reject. Подтверждение, что фоновые jobs не смогут отправить сообщения наружу.
4. Управляемый Messenger: наблюдать pending/in_progress/error/done, контролировать retries; read-only доступ к обезличенным логам, схеме и тестовой БД, медиахранилищу. Проверить cache/storage для job-status между web/worker.
5. Явно разрешённый лимит AI-вызовов либо детерминированные фикстуры/заглушки в существующем тестовом контуре; в этом аудите AI не запускался. Балансы 0, 1, несколько интервью, free-plan present/absent и настройка бесплатных тестов должны быть заранее подготовлены.
6. HH: отдельное разрешение и безопасный работодатель/OAuth-приложение с синтетическими/разрешёнными тестовыми сущностями. При отсутствии безопасного HH-контура ограничиться контрактными mocks; настоящий отклик/negotiation нужен для отправки, но получать его от реального кандидата не требуется и не запрашивается.
7. YooKassa test-shop, тестовые платежи и callback; доступ к безопасным журналам статусов без ключей. Никаких реальных карт/денег. Для C04 требуется проверка duplicate webhook и инфраструктурных ограничений входящих уведомлений.
8. Desktop Chrome и Android/iOS, разрешения микрофона/камеры, HTTPS, эмуляция потери сети/перезагрузки/фоновой вкладки. Синтетические аудио/видео и тексты трёх профилей из плана исследования.
9. Read-only доступ к настройкам/отчётам Метрики для проверки фактических целей, фильтров, SPA-навигации и исключения тестового трафика. Сырые cookie, токены, секреты и персональные записи не передавать в отчёт.

## 6. Ограничения и порядок дальнейшей проверки

Это аудит выборочных, но сквозных связей локального кода, не полный аудит безопасности/архитектуры и не ручной UX-тест. Не запускались приложение, debug:router, workers, миграции, запросы к API или платежам. Не проверены версия production, прокси/WAF, фактические тарифы/флаги/доступы HH, доставляемость писем, retention jobs и удаление файлов, качество AI, мобильная доходимость, конверсия, стоимость и время до результата.

Приоритет будущего безопасного теста: C01 (изоляция) → C04 (платёжный callback в sandbox) → C03 (удаление синтетических данных) → C05 (активация при email fail) → полный путь ручная вакансия/вопросы/ссылка/кандидат/отчёт/баланс → HH при безопасном контуре → C06–C09 → измерения воронки. detect-ai-resume сначала сверить с фактическим релизом без запуска обработки; локальный разрыв уже объяснён C02.

Не делать на основании этого отчёта обещаний о точности оценок, предсказании удержания, гарантированных 10 интервью, безлимите при любых настройках, работе детектора, безопасном удалении или production-изоляции до проверки соответствующего сценария.
