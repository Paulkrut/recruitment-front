# Схема измерения активации и контактов SofiHR

Дата: 29.10.2026. Источник — только локальный backend и frontend. БД, UI, `.env` и секреты не читались; SQL ниже не выполнялся. Это спецификация для проверки основным агентом на prod, а не результаты измерения. Другие документы не изменялись.

## 1. Единица анализа и достоверность схемы

Единица — **профиль компании `company.id`**, не человек, email, ИНН или HH employer. Один `user.id` состоит в нескольких компаниях через `employee`. Нельзя переносить активность пользователя/HH OAuth автоматически во все его компании. Одинаковое юрлицо может иметь несколько профилей: для данного измерения они остаются отдельными единицами.

ORM использует `doctrine.orm.naming_strategy.underscore_number_aware` (`config/packages/doctrine.yaml`): имена ниже — SQL snake_case из сущностей/миграций. Миграции исторические, местами отличаются от текущего ORM; до запуска агрегатов проверить `information_schema.columns`. Миграции billing явно MySQL/InnoDB; примеры рассчитаны на MySQL 8+ / совместимую MariaDB с CTE и JSON-функциями. Версию prod, фактическую схему и временную зону обязан проверить основной агент. Не запускать `schema:update` или миграции ради проверки.

### Компании, участники, телефоны, логины

- `company`: `id`, `name`, `logo`, `inn`, `hh_settings` (JSON). **Нет `created_at`, `updated_at`, owner, `is_demo`, `is_test`, `is_internal`, телефона или признака активации.**
- `employee`: `id`, `user_id`, `company_id`, `role`, `name`, `position`. Нет даты создания/присоединения. Роли участника, например `HR_LEAD`, `HR`, не путать с `user.roles`.
- `user`: `id`, `email` (уникальный), `phone` (nullable), `roles` (JSON), `email_verified`, `created_at`; `password` в аналитические SELECT не включать.
- Телефон компании как контакт HR: непустой `user.phone` у участника; отдельный номер заявки — `manager_consultation_bonus.client_phone`, `contact_message.phone`. `candidate.phone` и `hh_candidate.phone` — **кандидаты**, не клиентские лиды. Наличие номера не доказывает его валидность, доступность или согласие на обзвон. HH регистрация может заполнить `user.phone` из `hhProfile.personal_manager.phone`: это потенциально телефон персонального менеджера HH, а не клиента (`HhOAuthService`).
- При `/api/auth/login` парольный вход устанавливает `email_verified=1` при первом успехе; время и число входов в таблицах не сохраняются. JWT не является историей логинов. `PrivacyController` возвращает `lastLoginAt => null` с TODO.
- HH OAuth сразу создаёт `user.email_verified=1`. Поэтому это лишь proxy «подтверждённый email/вход через HH», **не доказательство первого парольного входа**. Нет `email_verified_at`, `first_login_at`, `last_login_at`.
- `/api/company` создаёт дополнительный профиль и участника напрямую, без `UserRegistrationService`: демо и приветственный бонус этим путём не начисляются. При принятии приглашения создаётся `employee`, сам `company_invite` удаляется: история членства неполна.
- `MIN(user.created_at)` среди текущих участников — только proxy возраста участников, **не дата создания компании**. Особенно неверно для второго профиля старого пользователя. Дата первого бонуса/вакансии тоже не гарантирует дату регистрации профиля.

### Вакансии, кандидаты, интервью, оценки

- `vacancy`: `id`, `company_id`, `created_by_id` → `employee.id`, `title`, `description`, `created_at`, `source`, `status`, `deleted_at`, `archived_at`, `public_token`, JSON `hh_import_settings`, `hh_auto_settings`, `interview_settings`; `source` по коду `manual`, `headhunter`, `linkedin`, а для демо **`demo`**. Статусы `active`, `archived`, `deleted`.
- `interview_template`: `id`, **`vacancy_id`** (владеющая связь OneToOne), `title`, `description`, `is_active`, `created_at`. `vacancy.template` — inverse ORM association, не использовать выдуманный `vacancy.template_id`.
- `vacancy.hhVacancy` и `candidate.hhCandidate` — inverse OneToOne ORM associations: **нет предполагаемых `vacancy.hh_vacancy_id` и `candidate.hh_candidate_id`**. SQL-связи идут через `hh_vacancy.internal_vacancy_id` и `hh_candidate.internal_candidate_id`.
- `interview_question.template_id` → шаблон; наличие вопросов проверять `EXISTS`, а не JOIN с размножением строк вакансий.
- `candidate`: `id`, `vacancy_id` (nullable), `employer_id` → `employee.id` (nullable), `name`, `email`, `phone`, `source`, `status`, `created_at`, `ai_score`, `ai_comment`, `ai_analysis_status`, `ai_analyzed_at`, `invitation_sent_at`, `reminder_sent_at`, `auto_rejected_at`, `auto_invited`, `last_contacted_at`, `last_message_from_candidate_at`, `communication_status`, `requires_attention`. Компания стандартно определяется через вакансию. Кандидатов без вакансии нельзя молча терять: отдельная группа; принадлежность можно исследовать через `employer_id`, но это не доказательство отсутствия demo.
- `interview_session`: `id`, `template_id`, `candidate_id` (nullable), `status` (`ready`, `in_progress`, `finished`), `created_at`, `started_at` (nullable), `analysis_status` (`pending`, `success`, `failed`, `partial`, nullable), `billing_processed`. **Нет `finished_at`, `analyzed_at`, `updated_at`.** `created_at` — создание сессии, не завершение, `started_at` — старт. Для компании предпочтителен путь `session.template_id → interview_template.vacancy_id → vacancy.company_id`; дополнительно проверить согласованность с вакансией кандидата.
- `interview_answer`: `id`, `session_id`, `question_id` → `interview_session_question`, `created_at`, `processing_status`, `score`, `answer_type`, `has_red_flag`, `text`, `choice_value`, имена медиафайлов. Это уровень ответа, а не интервью; использовать `EXISTS` для критерия наличия ответов. Время последнего ответа — proxy, не точное время завершения.
- `candidate_evaluation`: `id`, `candidate_id`, `status` (`pending`, `done`, `error`), `summary`, `strengths`, `weaknesses`, `metrics` (JSON), `error`, `created_at`, `updated_at`. Историческая миграция содержала `result`; ориентироваться на фактическую prod-схему, не предполагать одновременное наличие `result` и текущих JSON. `updated_at` — последнее обновление, не отдельное время успешного завершения. Один объект оценки может переиспользоваться/обновляться: число строк не равно числу запусков AI.
- Отдельный продукт: `regulation_test.company_id`, `created_by_id`, `created_at`, `updated_at`; `regulation_test_session.regulation_test_id`, `invitation_id`, `employee_id`, `status` (`new`, `started`, `finished`, `expired`), `created_at`, `started_at`, **`finished_at`**, `score`. Не смешивать эти сессии с `interview_session`.

### HH: авторизация ≠ подключённый employer API ≠ использование

- `hh_oauth_account`: `id`, `user_id` (unique), `hh_user_id`, `connected_at`, `last_sync_at`. Это **пользовательская** связь, не компания. Содержит также токены/профиль: их не выгружать.
- `hh_api_token`: `id`, `company_id`, `connected_by_id` → user, `integration_type` (`api`/`oauth`), `is_active`, `created_at`, `updated_at`, `expires_at`, `employer_id`, `manager_id`, `company_name`, `auto_sync`, `last_synced_at`; OAuth state имеет `oauth_state_created_at`. Токены и state не выгружать.
- `HhOAuthService::createHhApiTokenForCompany()` автоматически создаёт **неактивный placeholder** `integration_type='oauth'`, без access/refresh token. Простое `COUNT(hh_api_token)` существенно завышает интеграцию. Минимальный proxy подключения: `is_active=1`; более сильный факт — `last_synced_at IS NOT NULL` и/или реальные HH сущности. Если разрешено проверять доступность реквизита, возвращать только boolean наличия, никогда сам токен. Истечение срока не доказывает отсутствие исторического подключения.
- `hh_vacancy`: `id`, `company_id`, `hh_id`, `internal_vacancy_id`, `is_imported`, `status`, `created_at`, `updated_at`, `last_synced_at`, `candidates_sync_status`, `candidates_last_synced_at`, `candidates_total`, `candidates_synced`, `auto_sync_enabled`, `sync_interval_hours`, `needs_sync`, `hh_import_settings`. Это список/кэш HH; есть строка ≠ вакансия импортирована в основной продукт. Для импорта смотреть `is_imported`, ссылку `internal_vacancy_id` и существующую внутреннюю вакансию.
- `hh_candidate`: `id`, `company_id` (nullable), `hh_vacancy_id`, `hh_id`, `hh_resume_id`, `internal_candidate_id`, `is_imported`, `created_at`, `updated_at`, `response_date`, `screened_at`, `screened_by_id`, `last_contacted_at`, `interview_invitation_sent_at`, `interview_invitation_sent_by_id`, `interview_session_id`, `our_stage`, `stage`, `status`. Не суммировать `hh_candidate` и связанный `candidate` как двух людей. При nullable company использовать HH вакансию, проверив расхождения.

## 2. Как исключить автоматически созданные демо

`UserRegistrationService::createCompanyStructure()` при обычной и новой HH-регистрации вызывает `DemoDataService::createDemoData($company, false)`:

- 1 вакансия `title='Руководитель отдела продаж [ДЕМО]'`, **`source='demo'`**, `status='active'`;
- шаблон с 6 вопросами;
- **10 кандидатов**, у всех имя с `[ДЕМО]`, email `demo.<фамилия>@example.com`, но **`candidate.source='manual'`**, не `demo`;
- 10 готовых `candidate_evaluation.status='done'`, AI score и `ai_analysis_status='completed'`; `ai_analyzed_at` искусственно на 2 дня назад;
- 3 интервью `status='finished'`, `analysis_status='success'`, ответы с оценками, `started_at` искусственно на 3 дня назад;
- бесплатный стартовый баланс через `BillingService::addBonusInterviews`, категория транзакции `bonus`, `created_by_id=NULL`.

`app:demo:setup` может создать такой набор повторно, в любой компании и позднее регистрации; `--skip-interviews` меняет состав. Ошибка demo не блокирует регистрацию. Поэтому нельзя предполагать ровно один набор, вычитать «10 кандидатов и 3 интервью на компанию», определять demo только временем или считать компанию служебной из-за demo-вакансии.

**Детерминированная основа:** исключать `vacancy.source='demo'` и всю связанную цепочку `candidate`, `candidate_evaluation`, `interview_template`, `interview_session`, `interview_answer`. Сессию проверять и по вакансии шаблона, и по кандидату, если он задан: демо-кандидат мог оказаться в другом шаблоне. После перемещения кандидата полезны независимые сигнатуры `[ДЕМО]` и список 10 seed-email. Заголовок может быть переименован, source изменён, кандидат перемещён — абсолютной гарантии исторического происхождения нет: нет immutable `is_demo`/`seed_batch_id`. Такие случаи выделять `suspected_demo`, не объявлять доказанно реальными.

Для исторических подозрений: `[ДЕМО]` в вакансии/шаблоне/имени, шаблон seed-email, примерные seed-телефоны. Сам по себе `@example.com`, статус finished, наличие AI-оценки или `source='manual'` не надёжны. В SQL ниже conservative real = не `source=demo`, нет `[ДЕМО]`, нет seed-email; это операционная чистая группа, **не математическое доказательство живого клиента**.

### Служебные компании

В модели нет системного флага/утверждённого списка ID. Нельзя надёжно исключить их одним SQL по названию, почтовому домену или наличию `ROLE_ADMIN`: администратор может состоять в реальной клиентской компании. Нужен согласованный реестр **company_id + причина + кто подтвердил + дата** (вне БД для read-only исследования). В SQL выделен CTE `excluded_company`: заполнить подтверждёнными ID, не угадывать. Поиск `test`, `demo`, `SofiHR`, внутренних email — только кандидаты на ручную классификацию. Не исключать автоматически всех участников каждой компании служебного пользователя.

## 3. Определения активации

Считать ступени отдельно, не один неопределённый показатель:

1. `profile_exists`: профиль компании, после исключения подтверждённых служебных.
2. `member_verified_proxy`: есть текущий участник с `email_verified=1`; не компания-специфичный логин.
3. `real_vacancy_created`: есть недемо-вакансия; отдельно current active и all-time включая archived/deleted.
4. `real_vacancy_configured`: недемо-вакансия с шаблоном и хотя бы одним вопросом. Это настройка, не полученная ценность.
5. `hh_connected_proxy` / `hh_synced` / `hh_imported`: три разных стадии.
6. `real_candidate_received`: есть недемо-кандидат на недемо-вакансии. Ручная загрузка может быть собственным тестом HR; не гарантирует внешнего соискателя.
7. `real_screening_done`: недемо-кандидат с `candidate_evaluation.status='done'` и/или `ai_analysis_status='completed'`. Эти поля измерять отдельно; они могут рассинхронизироваться.
8. `real_interview_finished`: недемо-сессия `finished`, есть непустой ответ. `real_value_delivered`: дополнительно `analysis_status='success'`. `partial` учитывать отдельно. Это сильные доступные proxy, но не факт просмотра отчёта HR и не доказательство реального внешнего кандидата.
9. `paid_gateway_live` и `manual_activation`: отдельные признаки, описаны ниже.

`ManagerConsultationService::isCompanyFullySetup()` использует «вакансия с вопросами + 10 finished в этой вакансии», **без фильтра demo**. Для аналитики не использовать как готовую эталонную активацию.

Нет событий просмотра отчёта, полноценной истории авторизаций, завершения интервью с точным временем и company.created_at. Нельзя честно посчитать точный signup→first login, company-registration→activation за 1/7 дней или retention по посещениям из этих таблиц. Можно измерить текущее состояние, временные proxy и активность по созданию объектов; честно помечать семантику timestamp.

## 4. Оплата: gateway, ручная активация, бонусы

- `payment`: `id`, `company_id`, `subscription_plan_id`, `yookassa_payment_id` (unique), `status`, `amount` DECIMAL, `currency`, `description`, `metadata`, `yookassa_response` JSON, `created_at`, `updated_at`, `paid_at`, `canceled_at`.
- Статусы: `pending`, `waiting_for_capture`, `succeeded`, `canceled`, `failed`. Только `succeeded` — успех по внутренней модели. `paid_at` webhook устанавливает при переходе в success: это время обработки, не обязательно банковского расчёта.
- **Критическое исключение:** `ActivatePaidPlanCommand` создаёт `payment.status='succeeded'` и `paid_at`, но ID **`MANUAL_...`**, `metadata.manual_activation=true`, `metadata.activated_by_command=true`, `metadata.invoice_number`. Это ручная активация тарифа, а не автоматически подтверждённый платёж ЮKassa. Может соответствовать реальному счёту, но подтвердить документом/банком отдельно. При существующем `--payment-id` команда может начислять по существующему объекту: проверить количество ledger-строк на payment.
- Test gateway: `JSON_EXTRACT(yookassa_response, '$.test')=true` — исключить из live revenue. Отсутствующий `test` **не равно false**: выделять unknown, а не объявлять платёж live.
- Надёжный доступный proxy live: `status='succeeded'`, `amount>0`, не `MANUAL_`, metadata не manual, provider response `test=false` и `status='succeeded'`. Даже это внутренний слепок ответа: для финансовой сверки нужны реестр провайдера/возвраты, не только локальные записи.
- `transaction`: `id`, `company_id`, `payment_id` (nullable), `created_by_id` → user (nullable), `type` (`credit`/`debit`), `category`, `amount`, `interviews_changed`, `regulation_tests_changed`, `description`, `created_at`, `is_gifted`, `gift_value`.
- Покупка через `BillingService` создаёт `credit/purchase` со ссылкой payment. Бонус — `credit/bonus`, без payment, `created_by_id=NULL` для системного приветственного; non-null admin — ручное начисление. Остальные credit без payment — отдельная unlinked группа. В `debit` встречаются `interview_usage`, `interview_gifted`, `screening_usage`, `test_usage`; наличие списания не доказывает оплату.
- `company_balance`: `company_id` (OneToOne), `interview_balance`, `regulation_test_balance`, `total_interviews_purchased`, `total_interviews_used`, `total_regulation_tests_purchased`, `total_regulation_tests_used`, `created_at`, `updated_at`. **`total_interviews_purchased` не равно числу/объёму оплаченных интервью:** `addBonusInterviews` вызывает тот же `balance.addInterviews`, что покупка. Баланс/бонус не признак paid.
- `subscription_plan`: `id`, `code`, `name`, `price`, `interviews_included`, `is_free`, `is_active`, `created_at`, `updated_at`; тариф и текущая цена не историческая выручка.

Не соединять payment одновременно с employee/candidate/session/transaction и не суммировать размноженный `payment.amount`. `SUM(DISTINCT amount)` также неверен: два разных платежа могут иметь одинаковую сумму. Сначала агрегировать каждую факт-таблицу до company_id; деньги только из payment, ledger использовать для сверки через отдельную агрегацию/EXISTS.

## 5. Контакт менеджера, заявки и согласия

### Запись на консультацию

`manager_consultation_bonus`: `id`, `company_id`, `client_email`, `client_name`, `client_phone`, `meeting_scheduled_at`, `meeting_id`, `meeting_status`, `bonus_activated`, `bonus_activated_at`, `bonus_interviews_granted`, `last_banner_shown_at`, `banner_dismissed`, `created_at`, `updated_at`, `additional_data`.

`POST /api/manager-consultation/book` сохраняет booking с `meeting_status='scheduled'`. При отсутствующем email сервис пишет `<company.name>@temp.sofihr.ru` — это заглушка, не валидный адрес клиента. `created_at` — заявка, `meeting_scheduled_at` — назначенное время, не факт состоявшегося контакта. Наличие booking ≠ менеджер позвонил; `bonus_activated` не доказательство встречи или оплаты. `markConsultationShown`/`dismissConsultationBanner` в текущем сервисе только логируют: существование полей banner не гарантирует их заполнение.

`activateBonus()` обращается к отсутствующим в текущей `Company` методам `getInterviewsAvailable`/`setInterviewsAvailable`, а не `BillingService`; путь выглядит несовместимым с текущей моделью. Поэтому **не принимать эти поля за доказательство корректного зачисления** без проверки фактических данных. В `/book` не обнаружен вызов ConsentLogService, отдельное согласие не гарантировано.

### Публичные формы

- `/api/contact/submit` → `contact_message`: `id`, `name`, `email`, `phone`, `subject`, `message`, `created_at`. **Нет `company_id`, `user_id`, owner manager, contacted_at, статуса обработки/исхода.** Согласие сервер пишет `consent_logs.event='contact_form_submit'`, `subject_type='visitor'`, `subject_id=NULL`, `payload.contact_message_id` → message.id. Это заявка, не состоявшийся контакт.
- `/api/landing/contact` (callback/presentation) **не создаёт contact_message или отдельную lead-строку**: уведомление в Telegram + `consent_logs.event='landing_contact_form'`, `payload.type`, `has_email`, `has_company`, `has_comment`; имя/телефон/email/company в consent не сохраняются. В БД доступны числа событий, но нельзя восстановить контакт, уникальных лидов или связать их с company_id. Нельзя считать наличие consent доказательством доставки Telegram или звонка менеджера.
- Привязка contact_message к компании по `LOWER(TRIM(email))` допустима только как **inferred**. При user в нескольких профилях неоднозначна; телефон тоже может повторяться/быть общим. Хранить число возможных company_id и не разносить один лид как точный факт во все профили. Не выводить PII в рекламные отчёты.

### Consent

`consent_logs`: `id`, `subject_type` (`candidate`, `client`, `visitor`), `subject_id` VARCHAR nullable (не FK!), `event`, `policy_version`, `offer_version`, `ip_address`, `user_agent`, `payload` JSON, `created_at`.

Сервер регистрации пишет `subject_type='client'`, `subject_id=CAST(user.id AS CHAR)`, `event='register'`, payload `marketing`, `email_sent`. **Frontend `src/app/auth/register/page.tsx` отправляет `marketing_opt_in`, а AuthController читает `$data['marketing']`: реальный checkbox может записаться как false.** Нельзя объявлять эти false доказанным отказом и нельзя превращать согласие на ПДн/оферту в marketing opt-in. Для отдельного `marketing_opt_in` проверять payload/источник; одна строка с именем события без истинного значения/контекста не автоматическое юридическое разрешение. В показанной модели нет полноценного current marketing-consent state/истории отзывов.

`ConsentController` допускает event `login`, но актуальная `/auth/login` frontend-страница и backend AuthController не пишут такой consent как подтверждённый auth-event. Универсальный consent endpoint принимает переданные subjectId/payload: это не надёжный журнал входов. Сервер может писать события, не перечисленные в allowedEvents общего endpoint (например `landing_contact_form`). Кандидатские согласия не переносить на клиента компании.

### 6.2. Контроль demo: реальные и seed-объекты отдельно

```sql
SELECT v.company_id, v.source,
       COUNT(DISTINCT v.id) AS vacancies,
       COUNT(DISTINCT c.id) AS candidates,
       COUNT(DISTINCT e.id) AS evaluations,
       COUNT(DISTINCT CASE WHEN e.status='done' THEN e.id END) AS evaluations_done,
       COUNT(DISTINCT s.id) AS interview_sessions,
       COUNT(DISTINCT CASE WHEN s.status='finished' THEN s.id END) AS finished_sessions
FROM vacancy v
LEFT JOIN candidate c ON c.vacancy_id=v.id
LEFT JOIN candidate_evaluation e ON e.candidate_id=c.id
LEFT JOIN interview_session s ON s.candidate_id=c.id
GROUP BY v.company_id, v.source
ORDER BY v.company_id, v.source;
```

Это контрольная группировка **по source вакансии**, не окончательная clean-метрика. DISTINCT защищает счётчики от fan-out; никаких денежных сумм здесь нет. Для orphan/смешанных связей отдельно:

```sql
SELECT COUNT(*) AS candidates_without_vacancy FROM candidate WHERE vacancy_id IS NULL;
SELECT COUNT(*) AS sessions_without_candidate FROM interview_session WHERE candidate_id IS NULL;
SELECT COUNT(*) AS inconsistent_session_vacancies
FROM interview_session s
JOIN interview_template t ON t.id=s.template_id
JOIN candidate c ON c.id=s.candidate_id
WHERE c.vacancy_id IS NULL OR c.vacancy_id<>t.vacancy_id;
```

### 6.3. Company snapshot без размножения денег

В `excluded_company` изначально пустой список. До финального отчёта заменить на `SELECT <подтверждённый_id> AS company_id UNION ALL SELECT ...` или согласованный внешний список; не исключать произвольные компании.

```sql
WITH
excluded_company AS (
  SELECT id AS company_id FROM company WHERE 1=0
),
clean_vacancy AS (
  SELECT v.* FROM vacancy v
  WHERE COALESCE(v.source,'')<>'demo'
    AND COALESCE(v.title,'') NOT LIKE '%[ДЕМО]%'
),
clean_candidate AS (
  SELECT c.*, v.company_id
  FROM candidate c JOIN clean_vacancy v ON v.id=c.vacancy_id
  WHERE COALESCE(c.name,'') NOT LIKE '%[ДЕМО]%'
    AND LOWER(COALESCE(c.email,'')) NOT IN (
      'demo.morozov@example.com','demo.svetlova@example.com',
      'demo.volkov@example.com','demo.novikov@example.com',
      'demo.petrova@example.com','demo.smirnov@example.com',
      'demo.kovaleva@example.com','demo.belov@example.com',
      'demo.orlova@example.com','demo.sokolov@example.com')
),
member_stats AS (
  SELECT e.company_id, COUNT(DISTINCT e.user_id) AS users,
    MIN(u.created_at) AS earliest_current_member_signup_proxy,
    MAX(u.email_verified=1) AS member_verified_proxy,
    MAX(NULLIF(TRIM(u.phone),'') IS NOT NULL) AS has_member_phone
  FROM employee e JOIN `user` u ON u.id=e.user_id GROUP BY e.company_id
),
vacancy_stats AS (
  SELECT v.company_id, COUNT(*) AS real_vacancies_all_statuses,
    SUM(v.status='active') AS real_vacancies_active,
    MIN(v.created_at) AS first_real_vacancy_created_at,
    SUM(EXISTS(SELECT 1 FROM interview_template t
      WHERE t.vacancy_id=v.id
        AND EXISTS(SELECT 1 FROM interview_question q WHERE q.template_id=t.id)))
      AS real_vacancies_with_questions
  FROM clean_vacancy v GROUP BY v.company_id
),
candidate_stats AS (
  SELECT c.company_id, COUNT(*) AS real_candidates,
    MIN(c.created_at) AS first_real_candidate_created_at,
    SUM(c.ai_analysis_status='completed') AS resume_analysis_completed,
    SUM(EXISTS(SELECT 1 FROM candidate_evaluation e
      WHERE e.candidate_id=c.id AND e.status='done')) AS candidates_with_done_evaluation
  FROM clean_candidate c GROUP BY c.company_id
),
session_stats AS (
  SELECT v.company_id, COUNT(*) AS real_sessions,
    SUM(s.status='finished') AS real_finished_sessions,
    SUM(s.status='finished' AND s.analysis_status='success' AND
      EXISTS(SELECT 1 FROM interview_answer a WHERE a.session_id=s.id
        AND (NULLIF(TRIM(a.text),'') IS NOT NULL OR a.audio_filename IS NOT NULL
          OR a.video_filename IS NOT NULL OR a.choice_value IS NOT NULL)))
      AS real_finished_analyzed_with_answers,
    MIN(s.started_at) AS first_real_interview_started_at
  FROM interview_session s
  JOIN interview_template t ON t.id=s.template_id
  JOIN clean_vacancy v ON v.id=t.vacancy_id
  JOIN clean_candidate c ON c.id=s.candidate_id AND c.vacancy_id=t.vacancy_id
  WHERE COALESCE(t.title,'') NOT LIKE '%[ДЕМО]%'
  GROUP BY v.company_id
),
hh_stats AS (
  SELECT company_id, MAX(is_active=1) AS hh_active_proxy,
    MAX(last_synced_at IS NOT NULL) AS hh_ever_synced_proxy
  FROM hh_api_token GROUP BY company_id
),
payment_classified AS (
  SELECT p.*,
    CASE
      WHEN UPPER(LEFT(p.yookassa_payment_id,7))='MANUAL_'
        OR COALESCE(JSON_UNQUOTE(JSON_EXTRACT(p.metadata,'$.manual_activation')),'false')='true'
        THEN 'manual'
      WHEN JSON_UNQUOTE(JSON_EXTRACT(p.yookassa_response,'$.test'))='true' THEN 'gateway_test'
      WHEN JSON_UNQUOTE(JSON_EXTRACT(p.yookassa_response,'$.test'))='false'
        AND JSON_UNQUOTE(JSON_EXTRACT(p.yookassa_response,'$.status'))='succeeded'
        THEN 'gateway_live_proxy'
      ELSE 'gateway_unknown'
    END AS payment_class
  FROM payment p
),
payment_stats AS (
  SELECT company_id,
    SUM(status='succeeded' AND amount>0 AND payment_class='gateway_live_proxy') AS live_success_payments,
    SUM(CASE WHEN status='succeeded' AND amount>0 AND payment_class='gateway_live_proxy'
      AND currency='RUB' THEN amount ELSE 0 END) AS live_success_rub,
    MIN(CASE WHEN status='succeeded' AND amount>0 AND payment_class='gateway_live_proxy'
      THEN paid_at END) AS first_live_paid_at,
    SUM(status='succeeded' AND payment_class='manual') AS manual_success_records,
    SUM(status='succeeded' AND payment_class='gateway_test') AS test_success_records,
    SUM(status='succeeded' AND payment_class='gateway_unknown') AS unknown_success_records
  FROM payment_classified GROUP BY company_id
),
credit_stats AS (
  SELECT company_id,
    SUM(category='bonus' AND payment_id IS NULL AND created_by_id IS NULL) AS system_bonus_records,
    SUM(category='bonus' AND payment_id IS NULL AND created_by_id IS NOT NULL) AS manual_bonus_records,
    SUM(payment_id IS NULL) AS all_unlinked_credit_records
  FROM `transaction` WHERE type='credit' GROUP BY company_id
),
booking_stats AS (
  SELECT company_id, COUNT(*) AS consultation_records,
    SUM(meeting_scheduled_at IS NOT NULL) AS records_with_meeting_time,
    MIN(created_at) AS first_booking_created_at
  FROM manager_consultation_bonus GROUP BY company_id
)
SELECT co.id AS company_id,
  COALESCE(m.users,0) AS users, m.earliest_current_member_signup_proxy,
  COALESCE(m.member_verified_proxy,0) AS member_verified_proxy,
  COALESCE(m.has_member_phone,0) AS has_member_phone,
  COALESCE(v.real_vacancies_all_statuses,0) AS real_vacancies_all_statuses,
  COALESCE(v.real_vacancies_active,0) AS real_vacancies_active,
  COALESCE(v.real_vacancies_with_questions,0) AS real_vacancies_with_questions,
  v.first_real_vacancy_created_at,
  COALESCE(c.real_candidates,0) AS real_candidates, c.first_real_candidate_created_at,
  COALESCE(c.resume_analysis_completed,0) AS resume_analysis_completed,
  COALESCE(c.candidates_with_done_evaluation,0) AS candidates_with_done_evaluation,
  COALESCE(s.real_sessions,0) AS real_sessions,
  COALESCE(s.real_finished_sessions,0) AS real_finished_sessions,
  COALESCE(s.real_finished_analyzed_with_answers,0) AS real_value_delivered_sessions,
  s.first_real_interview_started_at,
  COALESCE(h.hh_active_proxy,0) AS hh_active_proxy,
  COALESCE(h.hh_ever_synced_proxy,0) AS hh_ever_synced_proxy,
  COALESCE(p.live_success_payments,0) AS live_success_payments,
  COALESCE(p.live_success_rub,0) AS live_success_rub, p.first_live_paid_at,
  COALESCE(p.manual_success_records,0) AS manual_success_records,
  COALESCE(p.test_success_records,0) AS test_success_records,
  COALESCE(p.unknown_success_records,0) AS unknown_success_records,
  COALESCE(cr.system_bonus_records,0) AS system_bonus_records,
  COALESCE(cr.manual_bonus_records,0) AS manual_bonus_records,
  COALESCE(cr.all_unlinked_credit_records,0) AS all_unlinked_credit_records,
  COALESCE(b.consultation_records,0) AS consultation_records,
  COALESCE(b.records_with_meeting_time,0) AS records_with_meeting_time,
  b.first_booking_created_at
FROM company co
LEFT JOIN member_stats m ON m.company_id=co.id
LEFT JOIN vacancy_stats v ON v.company_id=co.id
LEFT JOIN candidate_stats c ON c.company_id=co.id
LEFT JOIN session_stats s ON s.company_id=co.id
LEFT JOIN hh_stats h ON h.company_id=co.id
LEFT JOIN payment_stats p ON p.company_id=co.id
LEFT JOIN credit_stats cr ON cr.company_id=co.id
LEFT JOIN booking_stats b ON b.company_id=co.id
WHERE NOT EXISTS(SELECT 1 FROM excluded_company x WHERE x.company_id=co.id)
ORDER BY co.id;
```

Каждый fact-CTE отдаёт максимум одну строку на company_id, поэтому итоговая строка не размножает суммы. Для общего агрегата обернуть этот SELECT в CTE `company_snapshot` (убрав финальный ORDER BY), затем `COUNT(*)` профилей, `SUM(real_candidates>0)`/`SUM(real_value_delivered_sessions>0)`/`SUM(live_success_payments>0)`, `SUM(live_success_rub)`. Не суммировать количество пользователей профилей как уникальных пользователей платформы. Sessions без candidate и с несовпадающими vacancy намеренно исключены из строгого real и должны быть показаны отдельной unknown-группой.
